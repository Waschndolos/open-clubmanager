# Data model

Every device keeps its own SQLite database. The schema lives in
[`server/internal/db/migrations/`](../server/internal/db/migrations/) as goose
migrations that are embedded in the server binary and applied on every start
(`db.Open`). All SQL lives in [`server/internal/store/`](../server/internal/store/).

The schema is designed so that a sync layer can replicate changes between
devices as immutable, signed change files that are encrypted per **data scope**
(normative spec: [sync-protocol.md](sync-protocol.md)). The transport, segments,
encryption and identity are not implemented yet; the local groundwork (scopes,
field clocks, outbox, conflict detection) is. This document records the
conventions sync relies on.

## Conventions

| Topic | Rule |
| --- | --- |
| Primary keys | `TEXT` UUIDv7, generated by the application (`db.NewID`). Rows created offline on different devices never collide; v7 keeps inserts time-ordered. |
| Timestamps / dates | `TEXT`, UTC, `2006-01-02T15:04:05.000Z` (`db.TimeLayout`). Sorts lexicographically and works with SQLite's date functions. |
| Money | `INTEGER` cents (`amount_cents`, `purchase_price_cents`). The API still exposes decimal amounts. |
| Change tracking | Every synced table has `updated_at`, set from the HLC of the latest write. Every write to a synced table also records a field clock per written column and appends an op to the outbox, in the same transaction (see [Sync bookkeeping](#sync-bookkeeping)). |
| Deletion | Synced rows are never removed. Deleting sets `deleted_at` (a tombstone); all reads filter `deleted_at IS NULL`. Deleting a parent tombstones its dependants in the same transaction (e.g. a member's contact, bank details, links, fees and loans). |
| Uniqueness | Synced tables have **no** `UNIQUE` indexes: two valid changes from different devices may collide, and applying them must not fail. The rules (`db.UniqueColumns`: member number, contact e-mail, role/group/section name) are checked by the store before every local write, among live rows only, so a tombstone never blocks re-use. Collisions arriving through sync are flagged in `sync_conflicts`. Local tables (e.g. `users.email`) keep their `UNIQUE` indexes. |
| Links | `member_roles` / `member_groups` / `member_sections` have a composite key and are tombstoned and revived rather than deleted and re-inserted. |
| Connection | WAL journal, `foreign_keys=ON`, `busy_timeout=5s`, `BEGIN IMMEDIATE` transactions, one connection per process. |

## Scopes

A scope is the unit of permission and of encryption. A user (and therefore a
device) is granted a set of scopes; change files for other scopes are never
delivered to it, or cannot be decrypted. The table-to-scope mapping is the
registry `db.SyncedTables` in
[`server/internal/db/scopes.go`](../server/internal/db/scopes.go); a test
fails if a table is missing from it or lacks the sync columns.

| Scope | Tables | Contains |
| --- | --- | --- |
| `members.core` | `members`, `roles`, `groups`, `sections`, `member_roles`, `member_groups`, `member_sections` | Who is a member (number, name, birthday, entry/exit date, comment) and club structure |
| `members.contact` | `member_contacts` (1:1 with `members`) | E-mail, phone, mobile, street, postal code, city, state |
| `members.bank` | `member_bank_details` (1:1 with `members`) | Account holder, IBAN, BIC, bank name, SEPA mandate date |
| `finance` | `finance_transactions`, `member_fees` | Cash book and membership fees |
| `inventory` | `inventory_items`, `inventory_loans` | Club equipment and who has borrowed it |
| `admin` | – (ACL and club settings, not SQL tables in protocol v1) | |
| *local only* | `users`, `audit_log`, `user_preferences`, `refresh_tokens`, `password_reset_tokens`, `sync_*` | Device-bound state that must never be synced. `users` holds logins with password hashes; sync identity is the device. `audit_log` records this device's actions; the signed change files are the shared audit trail. |

A member without contact data or bank details has no row in the respective
table; clearing all fields of a part tombstones its row. This keeps scopes the
user has no data for empty.

### Field mapping of the former `Member` model

| Former field | New location | Scope |
| --- | --- | --- |
| `id` (int) | `members.id` (UUIDv7) | `members.core` |
| `number`, `firstName`, `lastName`, `birthday`, `entryDate`, `exitDate`, `comment` | `members.*` | `members.core` |
| `email`, `phone`, `phoneMobile`, `street`, `postalCode`, `city`, `state` | `member_contacts.*` | `members.contact` |
| `accountHolder`, `iban`, `bic`, `bankName`, `sepaMandateDate` | `member_bank_details.*` | `members.bank` |
| roles / groups / sections | `member_roles` / `member_groups` / `member_sections` | `members.core` |

Note that `member_fees` (scope `finance`) and `inventory_loans`
(`inventory`) reference `members.id`; a device holding `finance` or
`inventory` therefore also needs `members.core` to show whom a fee or loan
belongs to.

## Sync bookkeeping

All writes to synced tables go through the store's `writer`
([`server/internal/store/syncwrite.go`](../server/internal/store/syncwrite.go)).
In the same transaction as the data change it:

1. ticks the device's hybrid logical clock
   ([`server/internal/sync/hlc`](../server/internal/sync/hlc/)), persisted in
   `sync_device.hlc`, once per op;
2. writes only columns whose value actually changes (an unchanged update
   produces no op and keeps `updated_at`);
3. upserts `sync_field_clock (tbl, pk, col) → hlc, device_id` for each written
   column (`device_id` is NULL — "this device" — until the device identity exists);
4. appends the op (`{"t", "pk", "hlc", "set"}`, see sync-protocol §10) to
   `sync_outbox` with its scope.

`pk` in the sync tables is the JSON object of the primary key columns with
sorted keys (`op.EncodePK`). `store.DetectUniqueConflicts` implements the
uniqueness rule of sync-protocol §14.2 for the future apply step: among live
rows sharing a unique value, the one whose value has the smallest
`(hlc, device_id)` keeps it and the others are recorded in `sync_conflicts`.
Local writes re-run it for tables with open conflicts, so fixing a duplicate
clears its flag.

| Local table | Content |
| --- | --- |
| `sync_device` | One row: own `device_id` and key references (NULL for now), local HLC |
| `sync_field_clock` | Last writer per `(table, pk, column)` |
| `sync_outbox` | Local ops not yet written to a segment, in order, with scope |
| `sync_conflicts` | Rows flagged as duplicate of a unique value, with the row that keeps it |

Rows that existed before this bookkeeping (or were imported from a legacy
database) have no field clocks and no outbox entries; they count as oldest in
conflict resolution.

## Databases from earlier versions

Before the goose migrations, the server created Prisma-style tables (`"Member"`,
`"Role"`, `"_MemberRoles"`, … with integer ids). `db.Open` detects such a
database by its `"Member"` table, writes a copy next to it
(`<name>.pre-uuid-<timestamp>.db`), applies the migrations, copies all data into
the new tables with fresh UUIDs, and drops the old tables. Refresh and password
reset tokens are not carried over (they were unused). Restoring an old backup
goes through the same path.

## Adding a migration

1. Add `server/internal/db/migrations/000NN_description.sql` with
   `-- +goose Up` / `-- +goose Down` sections. Never edit a released migration.
2. New synced tables need a UUID `id`, `updated_at`, `deleted_at`, and an entry
   (scope and primary key) in `db.SyncedTables`; device-local tables go into
   `db.LocalTables`. Never add `UNIQUE` indexes to synced tables; add a rule
   to `db.UniqueColumns` and a `requireUnique` check in the store instead.
   Write synced tables only through the store's `writer`.
3. Put sensitive fields into a table of the narrowest scope rather than adding
   columns to a broader one.
